## Tickets

### SOCK-2: Show low stock badge next to price on product page when stock < 5
Problem: Shoppers cannot see when a product is close to selling out. The product details page should show a 'Low stock' badge next to the price when fewer than 5 units remain.

Approach:
(1) Server side, api/catalogue/index.js: the GET /catalogue* proxy (api/catalogue/index.js:10, using the catalogue URL from api/endpoints.js:18) should already forward /catalogue/{id}/stock to the catalogue service. Verify this, and only add an explicit route if the wildcard does not match. Do not add business logic in the proxy.
(2) Client side, product details page under public/: after the product details load, call GET /catalogue/{id}/stock with jQuery. If stock is below 5, render a badge element next to the price. If the call fails or returns non-200, render no badge and leave the rest of the page working. The wiki does not name the details page HTML/JS files, so the exact file names are unclear and the implementer should confirm them in public/. Put the threshold of 5 in one named constant, for example LOW_STOCK_THRESHOLD = 5.

Out of scope: badges on list or category pages, blocking add-to-cart when stock is 0, showing the exact count, and real-time stock updates.
Acceptance criteria:
- Given the catalogue service reports stock 3 for product X, when a shopper opens the product details page for X, then a 'Low stock' badge is shown next to the price
- Given the catalogue service reports stock 5 for product X, when a shopper opens the product details page for X, then no low stock badge is shown (the threshold is strictly fewer than 5)
- Given GET /catalogue/X/stock returns 404, 500 or times out, when a shopper opens the product details page for X, then no badge is shown, price and product details render normally, and the browser console shows no unhandled error
- Given the front-end is running with the catalogue service reachable, when a client calls GET /catalogue/X/stock on the front-end (port 8079), then the request is proxied to the catalogue service and returns its status and JSON body unchanged
- Given the stock request has been proxied, when an operator scrapes GET /metrics on the front-end, then http_request_duration_seconds has a sample for the stock request with service='front-end'
Test notes:
- (unit) Mocha/Chai/Sinon: stub the catalogue HTTP call and assert that GET /catalogue/:id/stock on the Express app proxies to the catalogue URL from api/endpoints.js and passes through 200 and 404 responses.
- (unit) If the badge decision is moved into a small pure function (for example shouldShowLowStock(stock)), test it with Mocha/Chai at stock values 0, 4, 5 and 10, and with undefined.
- (e2e) Extend the catalogue flow in test/e2e/ (make e2e). Open a product whose seeded stock is below 5 and assert the badge is next to the price. Open one with stock of 5 or more and assert there is no badge.
- (manual) In a browser, open the details pages for a low-stock product and a well-stocked product. Then stop the catalogue service and reload. The page should render without a badge and without breaking.

## Agent notes

Status: all five acceptance criteria are met. They are covered by unit tests and were checked by hand against a fake catalogue service, with the front-end on port 8079 and the details page loaded in headless Chrome. The e2e suite was not run (see below).

- **Proxy: an explicit route was needed (approach step 1).** The `/catalogue*` wildcard does match `/catalogue/{id}/stock`. But `helpers.simpleHttpRequest` always answers 200 and drops the upstream Content-Type, so AC4 ("returns its status and JSON body unchanged") failed through the wildcard. A 404 came back as 200. `api/catalogue/index.js` now has a `GET /catalogue/:id/stock` route, registered before the wildcard. It passes the upstream status, Content-Type and body through unchanged, with no business logic. Connection errors go to `next(err)`, so the existing `errorHandler` returns a 500. `simpleHttpRequest` and the wildcard are unchanged, so other catalogue routes behave as before. `test/api/catalogue_test.js` pins this.
- **Details page files.** The page is `public/detail.html`. The badge logic is in the new file `public/js/stock.js`: `LOW_STOCK_THRESHOLD = 5`, a pure function `shouldShowLowStock(stock)`, and `showLowStockBadge(id, $price)`. The page calls `showLowStockBadge` right after it sets the price. The badge is a Bootstrap `label label-warning` span appended inside `#price`. `stock.js` exports through `module.exports` when that exists, so Mocha can `require` it.
- **Failure handling (AC3).** The stock call is `$.ajax` with `dataType: "json"` and a 3s timeout. Its error callback only logs with `console.log`, so nothing is thrown. Checked in headless Chrome for upstream 404, 500 and an 8s hang. In each case the price and details rendered, no badge appeared, and there were no uncaught exceptions. A non-numeric or missing `stock` also shows no badge.

The path label is the first path segment, not `/catalogue/{id}/stock`, by design (it avoids high cardinality). Unit-tested, and checked against a live `/metrics` scrape.
